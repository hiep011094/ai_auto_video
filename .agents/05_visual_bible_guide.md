# 05 — Guide to Building `visual_bible.json`

## 1. Why this file is required

Every scene is generated by VEO 3.1 from its own separate prompt — there is
no model-level transition connecting scenes to each other. If every
`veo_prompt` re-describes characters/locations its own way, viewers will see
the character's face "change" and the setting's color "shift" between
clips when they're stitched together — completely breaking the realistic
cinematic feel. `visual_bible.json` is the single "source of truth" that
every `veo_prompt` must reference verbatim.

## 2. When to create it

Right after Step 5 (splitting into chapters) and **before** Step 7
(splitting into scenes) / Step 8 (writing veo_prompts) in `01_workflow.md`.
Create it **exactly once for the whole video** — even for a long video with
many chapters.

## 3. How to fill in each section

### `story_anchor`
Write this **first**, before any other section — 2 to 4 sentences
capturing the whole video's throughline: the central question/hook it
opens with, the main thread that runs through the body, and where it lands
by the end. This is the fix for a specific failure mode: `context_ref`
(used when writing each `veo_prompt`, see `06_veo_prompt_guide.md §1`) only
gives visibility into the current sentence, not the video's overall arc. On
a multi-chapter Long video, an agent processing chapter 4 in isolation can
lose track of the throughline established in chapter 1 if it has nothing
but chapter 4's local text in front of it.

`story_anchor` solves this **without** requiring a full re-read of
`master_script.txt` before every single scene (which would multiply token
cost across dozens of scenes for little added benefit). Re-reading these
2–4 sentences once per scene is enough to keep every `veo_prompt` — even in
chapter 6 of a Long video — visibly serving the same story as chapter 1.
Reserve a full re-read of `master_script.txt` for genuine ambiguity only
(see `06_veo_prompt_guide.md §1`, item 4).

Example:
```
"story_anchor": "Video này hướng đến một câu hỏi cốt lõi: vì sao càng cố nắm giữ, con người lại càng khổ? Mở đầu bằng một tình huống đời thường về sự chấp trước, dẫn dắt qua lời dạy về Vô thường trong Kinh Pháp Cú, và kết thúc với bài học rằng buông bỏ không phải là mất mát mà là tự do thật sự."
```

### `characters`
For every character appearing in 2 or more scenes (including a reconstructed
historical figure), describe:
- Fixed appearance: face geometry, estimated age, hair shape/length, build/proportions, skin/eye characteristics when relevant, and 2–4 unmistakable non-sensitive identity markers
- Fixed outfit: exact garment type, material, color, fit, footwear/accessories; unchanged between scenes unless the script deliberately
  changes it over time (if so, state exactly where that change happens)
- Their role in the video (narrator figure, a monk/teacher being depicted,
  a historical figure, a lay practitioner, ...)

**Buddhist-specific character guidance:**
- Monks/nuns: generic appearance per Veo policy — never depict a real identifiable teacher. Describe robe color/style (saffron for Theravada, grey/brown for Vietnamese Mahayana, maroon for Tibetan), head shaved, bare feet or sandals.
- The Buddha: depict as a generic meditating figure or silhouette, not a specific statue style. Never claim to show the "real" appearance.
- Lay practitioners: generic Vietnamese adults in modest everyday clothing.

### `locations`
For every setting/location appearing in 2 or more scenes: describe its
architecture/terrain, **stable spatial topology**, dominant materials/colors, and identifying features, so every `veo_prompt` references the same description. Include durable left/right/front/back relationships when they matter (e.g. window wall behind the main desk, entrance camera-right, telescope dome beyond the north-facing glass), stable scale, floor/ceiling treatment, and 2–4 fixed landmarks. This prevents the same lab/room/landscape from being regenerated with a completely different layout in later clips.

### `key_objects`
Only declare objects with a recurring role (a meditation bell, an alms bowl,
a lotus flower, a sacred text, an oil lamp, ...). Record stable geometry, material, scale, orientation markers, and characteristic surface/light behavior. No need to declare an object that appears only once.

**Buddhist recurring visual elements:**
- Lotus flowers: specify color (white = purity, pink = devotion), stage (bud/bloom/full), water setting
- Alms bowls: dark lacquer or metal, round, carried at waist height
- Meditation bells/singing bowls: bronze/brass, specify size
- Oil lamps/candles: warm amber glow, specify holder type
- Bodhi tree: heart-shaped leaves, massive trunk, dappled light underneath
- Incense: thin smoke wisps rising, specify holder

### `visual_style`
Set once: aspect ratio (`9:16` for SHORT/vertical videos, `16:9` for LONG/horizontal videos), film-look style (recommended:
"premium cinematic Buddhist visual storytelling, mature semi-realistic 3D, warm amber tones, soft natural light, subtle film grain, high detail, physically grounded materials"),
dominant color grading — this can vary by scene type (e.g. warm golden for
temple/outdoor scenes, soft candlelit amber for meditation/interior scenes,
misty blue-grey for mountain/dawn scenes) but you must state explicitly
**when each grade applies**.

For scene-type-specific color grading instead of a universal warm amber,
reference `references/color_palette_system.md`. The `color_grading` field
should specify which palette applies to which scene type, following the
channel's 7 standard palettes (A–G). The `film_look` anchor remains
universal; color variation comes through `color_grading` and
`lighting_timeline` only.

**Mature 3D rule:** semi-realistic 3D is the default, but it must never look like children's animation. Favor natural facial proportions, restrained expressions, believable skin/fabric/stone/wood, subtle atmospheric depth, and physically plausible light. Sacred figures and settings must feel dignified rather than cute, toy-like, glossy, or game-like.

**Prompt-reuse rule:** `film_look` is the canonical global look anchor. Every final `veo_prompt` must include this exact `film_look` wording **once and only once**. This is how independently generated clips retain one common film identity. Do not paste it multiple times, and do not rewrite it scene-by-scene.

### `lighting_timeline`
Lay out the chronological time-of-day progression through the video, by
major chapter/scene stage, to avoid illogical lighting jumps. Example:
```json
[
  { "stage": "opening (hook)", "time_of_day": "dawn", "mood": "quiet curiosity, gentle awakening" },
  { "stage": "body", "time_of_day": "morning to midday / temple interior", "mood": "contemplative, warm, insightful" },
  { "stage": "ending", "time_of_day": "golden hour / candlelit evening", "mood": "peaceful resolution, gentle opening" }
]
```

### `camera_style`
Set the simulated lens type and the channel's characteristic camera-movement
style, so `veo_prompt` never has to reinvent this each time — it only
selects the variant that fits each scene's `shot_type`.

### Carrying `continuity_ref` across different `chapter_0X.json` files (multi-chapter Long videos)

`continuity_ref` describes the end state of the **immediately preceding
scene in the whole video**, not just the preceding scene within the same
JSON file. Since each chapter is its own file, when starting to write
`veo_prompt`s for chapter 2 onward:

- The first scene of `chapter_0X.json` (X ≥ 2) **must not** say `"opening"`
  — only the very first scene of the whole video (scene 1 of
  `chapter_01.json`) is allowed to say `"opening"`.
- The `continuity_ref` of the first scene in a new chapter must describe the
  actual end state of the **last scene in `chapter_0(X-1).json`** (character
  position, gaze direction, lighting, time of day) — the agent must open the
  previous chapter's file to get this right, never guess or leave it blank.
- If the script deliberately time-skips between 2 chapters (e.g. moving from
  "body" to "ending" in `lighting_timeline`), `continuity_ref` must state
  clearly that this is an intentional time jump (e.g. `"continuing from
  [description of the previous chapter's last scene], time-skip to dawn the
  next day"`), matching `07_qa_checklist.md` section B.

`continuity_ref` is an **editorial handoff from the previous visible end state only**, not a story-outline field and not a demand that every two
clips belong to one physically unbroken take. It must never preview the next argument, import a later `part`, switch to the opposing side of a debate before the current `voiceover` does, or introduce a later speculative result. Use the previous end state to
choose the correct relationship:

- **continuous action:** same subject/location/time — preserve pose, gaze,
  screen direction, object state, weather, and motivated light;
- **matched conceptual cut:** narration changes visual subject but continues
  one idea — preserve a useful visual anchor such as motion direction, shape,
  scale, or color/light when it improves the edit;
- **intentional location/time shift:** narration clearly moves elsewhere —
  state the previous end state and the intentional shift so the next prompt
  does not look like an accidental reset.

This keeps the long video coherent without forcing artificial "teleport-free"
physical continuity between documentary illustrations that are supposed to be
separate places or times.

### `negative_keywords`
Minimum required list, in two groups:
- **Visual quality**: watermark, text overlay/burned-in text, logo, obvious toy-like/childish cartoon CGI, exaggerated anime/chibi proportions, flat 2D illustration, anachronistic modern details (when the
  topic is set in the past or an ancient hypothesis).
- **Policy safety** (required by `12_veo_policy_compliance.md §4` — never
  omit these): no real identifiable people, no celebrity likeness, no
  graphic violence, no gore, no nudity, no sexual content, no hate symbols.

### Human characters must always be generic/anonymized
Per `12_veo_policy_compliance.md §2.1`, no entry under `characters` may
describe the real likeness of a named real person — even when
`master_script.txt` names that person in narration (e.g. a real historical
scientist). Write every human character as a fictional/generic persona
("an elderly male physicist, generic appearance, not modeled on any
specific real individual") the same way this project already handles
figures like "Tiến sĩ Nguyễn Văn A." This keeps every `veo_prompt` that
reuses the description automatically compliant.

### Canonical-description discipline (important for the 4,000-character prompt limit)

`visual_bible.json` remains the exact text source for recurring identity, but
its canonical descriptions should be **compact and discriminative**, not
novel-length prose. For each recurring entry, prioritize the few attributes
that prevent drift:

- character: age range/build, face/hair, 2–4 unmistakable identity markers,
  fixed outfit/material/color, and only story-relevant accessories;
- location: architecture/terrain, spatial layout, 2–4 stable landmarks,
  dominant material/color, and stable environmental conditions;
- key object/phenomenon: scale, geometry, material/surface, color/energy
  behavior, and physically meaningful motion.

Do not repeat global film-look adjectives inside every character/location
entry; keep those in `visual_style`/`camera_style`. This preserves exact reuse
while leaving enough of each `veo_prompt`'s 4,000-character budget for the
actual scene beat, continuity, weather/physics, and cinematography.

### Dynamic state versus fixed identity

The visual bible stores **fixed identity**. Scene-to-scene changing state
(position, pose, gaze, opened/closed doors, dust level, rain intensity,
object damage, sun position, etc.) belongs in `continuity_ref` and the current
scene action. Never rewrite a fixed character/location description just to
encode a temporary state change.

For weather or natural phenomena that persist across multiple scenes, anchor
the stable condition in the location/lighting plan, then carry the changing
intensity/direction through `continuity_ref`. This prevents rain, fog, wind,
cloud cover, particle fields, water level, shadows, or similar phenomena from
randomly resetting between clips.

## 4. Reuse principle when writing veo_prompt

When writing `veo_prompt` for each scene (Step 8), **copy the exact wording**
of only the **relevant** character/location/object description(s) from
`visual_bible.json` — never paraphrase identity anchors into different words.
Descriptions should already have been authored compactly per the section
above. Do not paste unrelated bible entries merely for completeness: prompt
budget is reserved for the current beat. Wording consistency across prompts
matters, but the final prompt must still remain within the 900–4,000 total-character production range with >=800 positive visual characters before Negative.


## 5. Alias and era identity lock

A recurring entity can be referred to by more than one phrase in narration/prompt. Use optional `aliases` to map those phrases back to one canonical visual identity. Example: location `Ancient Green Sahara Oasis (Prehistoric Richat)` may use aliases `Green Sahara`, `prehistoric Sahara`, `humid Sahara`. If any alias is used in a `veo_prompt`, the exact canonical description is still required.

Do **not** use aliases to merge visually different eras. If the same generic role appears with materially different appearance/outfit/equipment (for example a Gemini-era astronaut versus a modern ISS astronaut), create separate character entries with distinct names and optional `era` values. Their canonical anchors must remain separate. This prevents the QA layer from mistaking an intentional era change for drift—or, worse, allowing accidental drift because both were called `Generic Astronaut`.

### V9 mandatory no-edit negatives

In addition to topic/style/policy negatives, every new visual bible must include these entries in `negative_keywords`: `internal cuts`, `scene transitions`, `fades`, `dissolves`, `morph transitions`, `montage`, `time jumps`, `location changes`, `visual-domain changes`.

Every final prompt still carries the exact combined lock in its Negative clause: `internal cuts, scene transitions, fades, dissolves, morph transitions, montage, time jumps, location changes, visual-domain changes`. This is intentionally redundant: visual-bible reuse protects consistency while deterministic prompt QA verifies the exact clip-level contract.
